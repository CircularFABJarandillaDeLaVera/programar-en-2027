Empresario y trabajador · Autenticación y autorización

DESCARGAR PRÁCTICA

Objetivo: separar empresa y trabajador, autenticar usuarios y hacer que FastAPI autorice cada operación.

La nueva necesidad

Ya sabemos fichar con una interfaz web y guardar ubicación aproximada. Ahora aparece un problema real: no todas las personas deben poder hacer lo mismo.

EMPRESA
-> crear trabajadores
-> consultar fichajes

TRABAJADOR
-> fichar entrada
-> fichar salida
-> ver su propio historial

El trabajador no debe poder usar operaciones administrativas aunque conozca la URL.

AUTENTICACIÓN

Autenticarse es demostrar quién eres. Autorizar es comprobar que esa persona puede realizar una operación concreta.

Dos interfaces

/app/empresa/
  -> crear trabajadores
  -> ver trabajadores
  -> consultar fichajes

/app/fichar/
  -> fichar entrada
  -> fichar salida
  -> ubicación opcional
  -> estado propio
  -> historial propio

Separar pantallas ayuda a que cada persona vea lo que necesita. Pero la autorización real no depende de esas pantallas: depende de FastAPI.

401 y 403

401 Unauthorized
= no estás autenticado

403 Forbidden
= sabemos quién eres, pero no tienes permiso

Si alguien no ha iniciado sesión e intenta usar un endpoint protegido, FastAPI responde 401. Si un trabajador autenticado intenta usar una operación de empresa, FastAPI responde 403.

Autorización real

TRABAJADOR
   ↓
POST /trabajadores
   ↓
FastAPI comprueba rol
   ↓
403 FORBIDDEN

Ocultar un botón no es autorización. Aunque el trabajador invoque directamente POST /trabajadores desde Swagger o desde otra herramienta, FastAPI comprueba el rol y rechaza la operación.

Identidad del servidor

cookie
  ↓
sesión
  ↓
usuario autenticado
  ↓
trabajador_id real
  ↓
fichaje

La interfaz de fichar no decide a qué trabajador pertenece el fichaje. FastAPI lee la sesión, localiza el usuario autenticado y usa el trabajador_id real asociado a ese usuario.

Incluso si alguien intenta enviar otro trabajador_id, el servidor no debe usarlo para decidir la identidad.

Trabajador no es usuario

trabajadores
  id
  nombre

usuarios
  id
  usuario
  password_hash
  rol
  trabajador_id

Un trabajador representa una persona del negocio. Un usuario representa una identidad que puede acceder al sistema.

EMPRESA
usuario
rol = EMPRESA
trabajador_id = NULL

TRABAJADOR
usuario
rol = TRABAJADOR
trabajador_id -> trabajadores.id

Contraseñas

Una contraseña nunca debe guardarse en texto plano. Tampoco basta con aplicar un SHA-256 directo a la contraseña.

  • La práctica utiliza PBKDF2.
  • Cada contraseña usa un salt aleatorio.
  • La comparación se hace de forma segura.
  • La base de datos guarda password_hash, no la contraseña original.

No usamos JWT, OAuth ni OpenID Connect. Es una solución pedagógica para entender autenticación y autorización antes de introducir sistemas más complejos.

Seguimos trabajando en localhost con HTTP. HTTPS llegará más adelante, cuando abordemos acceso real desde móvil.

PROBAR

  1. Preparar PostgreSQL y .env.
  2. Arrancar FastAPI.
  3. Entrar en /app/empresa/.
  4. Iniciar sesión como empresa.
  5. Crear un trabajador con usuario y contraseña.
  6. Entrar en /app/fichar/.
  7. Iniciar sesión como trabajador.
  8. Fichar ENTRADA y SALIDA.
  9. Comprobar que el trabajador solo ve sus propios fichajes.
  10. Probar desde Swagger que un trabajador recibe 403 al intentar POST /trabajadores.

MINI-RETO

Usa tu agente de programación para hacer un cambio pequeño de autorización. Primero pide análisis:

Analiza esta aplicación.

NO modifiques nada todavía.

Después, si la propuesta es razonable, autoriza un cambio pequeño:

Aplica únicamente el cambio necesario para que la empresa pueda ver el nombre de usuario asociado a cada trabajador en la respuesta de listado.

Mantén la autorización en FastAPI.
No permitas que un trabajador vea la lista de trabajadores.
Añade o adapta las pruebas necesarias.
No hagas Git.

Revisa git diff, ejecuta tests y haz una prueba manual. El objetivo no es confiar en el agente: es dirigirlo, revisar lo que cambia y validar el resultado.
